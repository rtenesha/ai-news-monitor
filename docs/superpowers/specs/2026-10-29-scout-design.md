# Дайджест «ИИ-скаут» — дизайн

Спека по инструкции редактора «Агент ИИ-скаут» (полный текст от 2026-10-29).
Дата: 2026-10-29. Статус: на утверждении.

## 1. Замысел

Отдельный редакторский конвейер, который ищет **необычные, свежие, потенциально
вирусные ИИ-истории** для Zerocoder — не обычный агрегатор. Цель — подборка 5–10
проверенных инфоповодов с первоисточниками, из которой редактор быстро выбирает
темы для постов. Редактор сам решил, что лучше пять проверенных историй, чем
двадцать пересказов релизов.

Целевые сюжеты — 6 рубрик из инструкции:

- **А. Роботы и научные эксперименты** — роботы учатся действиям, странные
  эксперименты, прототипы «как из фантастики», новые способы управления.
- **Б. Необычные применения ИИ** — ИИ в непривычной сфере, ИИ в бытовых
  предметах/одежде/транспорте, необычные интерфейсы.
- **В. Провалы и курьёзы** — абсурдные результаты, ошибки контекста,
  неожиданные последствия автоматизации. Не придумывать, не преувеличивать.
- **Г. Новые инструменты и ИИ-агенты** — необычные сервисы, автоматизация
  рутины, агенты без программирования, open-source, неочевидные приёмы с
  Claude Code / ChatGPT / Gemini / локальными моделями. Обычные анонсы моделей
  без интересной особенности — не включать.
- **Д. Будущее профессий и общества** — прогнозы, исследования о людях и ИИ,
  этические дилеммы. Отделять факты от мнений.
- **Е. Деньги и закулисье индустрии** — стоимость моделей/агентов, бизнес-
  истории. Всегда уточнять смысл сумм (выручка/расходы/инвестиции/оценка).

## 2. Решения редактора (фиксируем как есть)

- Форма: **команда бота `/scout [часы]`** — по образцу `/digest` и `/tools`.
  Не автоотправка; рубильник `TELEGRAM_AUTO_SEND` её не гейтит.
- Вывод: **короткий список-оглавление** (как `/digest`), полная карточка по
  номеру — **`/scout <N>`** (нумерация совпадает с оглавлением).
- **TechCrunch AI возвращается** в источники (решение редактора от 2026-10-29
  отменяет октябрьское же исключение TechCrunch — но только для скаута;
  `monitor.py`/`notifier.py` своим списком `FEEDS` не трогаем).
- Окно по умолчанию **48 ч**, аргумент 2–168 (как у `/digest`, но дефолт шире —
  редактор смотрит подборку не чаще пары раз в день).

## 3. Цели, не-цели, анти-цели

**Цели:** регулярная короткая подборка необычных историй; каждая с проверяемым
первоисточником и честным статусом проверки; фильтр «вирусного потенциала» по
критериям раздела 5 инструкции.

**Не-цели:**
- не писать готовые Telegram-посты (только карточку-фактуру и визуальную идею —
  «не пиши полноценный пост без отдельного запроса»);
- не менять `monitor.py`/`notifier.py` и их ленты;
- не дублировать `/digest`: там — рабочий конвейер карточек по 6 рабочим
  критериям, `/scout` — фильтр именно необычного/вирусного по своей шкале.

**Анти-цели (провал, даже если код работает):** выдуманные провалы и ссылки;
выдача старой истории за новую; подборка проходных релизов «для количества»;
про «ИИ заменит всех» без подтверждения.

## 4. Архитектура

Новый модуль **`scout.py`** (по образцу `tools_digest.py`: pipeline без
Telegram-зависимостей) + три тонких хендлера в `bot.py`:

```
collect_scout_topics(hours)        → кандидаты (dedup + рубричный фильтр + кап)
select_scout_topics(cands, client) → 5–10 тем, AI-скоринг по 5 критериям
/scout                    → render_scout_list()          (короткий список)
/scout N                  → build_scout_card() + фактчекинг + рендер
```

Хендлеры: `/scout` без аргумента и с числом-номером — различаем как `/digest` и
`/card`: число 1–10 = номер карточки, иначе окно часов. Список тем хранится в
`bot_data["scout_topics"]`, seen-url карточек — в `bot_data["scout_seen"]`
(карточку одной темы строим один раз — `get_or_build_scout_card`, повторный
`/scout N` не жжёт второй AI-вызов; url показанной темы выпадает из следующих
прогонов через `filter_unseen` — механика `editorial.py`).

Модель — `openai/gpt-oss-120b`, `reasoning_effort="low"`, системные промпты с
`_NATURAL_TEXT_RULES` — без изменений по сравнению с `notifier.py`/`editorial.py`.

## 6. Конвейер сбора: `collect_scout_topics(hours)`

1. Слив всех источников → `dedup_cross_source` (как в `editorial.collect_topics`).
2. **Рубричный фильтр** — шире `KEYWORDS`: `SCOUT_KEYWORDS` добавляет слова
   рубрик А–Е к базовым спискам из `notifier.py` (`robot`/`робот`, `demo`,
   `video`/`видео`, `research`/`исследован`, `study`, `fail`/`провал`,
   `backfire`, `hallucinat`/`галлюцинац`, `expensive`/`стоимость`,
   `billion`/`млрд`, `jobs`/`професси`, `experiment` и т.п. — точный состав за
   имплементатором; матчинг стемами, как в `tools_digest._stem_matches`, чтобы
   работали русские основы).
3. Кап кандидатов **20** по keyword-баллу (`score_article` + бонусы за слова
   рубрик — точные веса за имплементатором).

## 7. AI-скоринг: `select_scout_topics()`

Как `editorial.select_topics`: полнотекстовая экстракция
(`extract_full_text`) → один вызов на кандидата → JSON со строгой валидацией
(total **пересчитывается кодом**, число модели игнорируется; мусорная форма →
None → фолбэк на keyword-оценку для этой статьи, `ai=False`).

Пять критериев из раздела 5 инструкции, каждый 0–2:

- **неожиданность** — есть ли в истории что-то необычное
- **наглядность** — можно ли показать фото/видео/скриншотом/простой схемой
- **понятность** — объяснима без сложного технического контекста
- **релевантность** — интересна аудитории Zerocoder (ИИ и вайбкодинг)
- **потенциал обсуждения** — удивление, спор, улыбка, желание поделиться

Пороги (константы в `scout.py`): **8–10 — приоритет**, **6–7 — резерв**,
**< 6 — отброшено** (в AI-режиме). Заодно скорер возвращает `category` (А–Е
или «пустышка» → тем же механизмом, что рубрика «Инфоповод-пустышка» в
`editorial.py`) и `one_liner`. Max списка — **10** (`SCOUT_LIST_MAX`),
инструкция требует 5–10 и прямо запрещает заполнять проходнём.

Разрешение коллизии с `/digest`: скорек поощряет «удивление» и «наглядность»,
а не пользу — так списки не сольются; плюс `scout_seen` отдельный.

## 8. Карточка `/scout N`: `build_scout_card()` + фактчекинг

Один AI-вызов по полному тексту (как `editorial.build_card`) — поля по шаблону
раздела 7 инструкции, все текстовые поля через `clean_text`, JSON-валидация с
дефолтами (как `_parse_card_json`):

1. **hook** — заголовок-крючок на русском, передаёт суть, не обманывает
2. **what_happened** — кто, что и когда сделал, 2–4 предложения
3. **why_interesting** — чем выделяется для аудитории, 1–2 предложения
4. **post_format** — один из фиксированных: новость с объяснением /
   необычный эксперимент / забавный провал / практический разбор инструмента /
   дискуссионный пост / короткий видеопост / опрос аудитории
5. **visual** — какой есть визуал (видео/фото/скриншот/демо) или «не найден»;
   ссылка на визуал из текста материала, если есть. Происхождение вирусных
   видео автоматически не проверить — если в материале нет подтверждения,
   модель обязана писать «происхождение не проверено»
6. **sources** — первоисточник (url статьи) + доп. корроборация (см. ниже)
7. **score** — итог/10 и краткое объяснение. Объяснение строит AI-вызов
   карточки (он и так читает полный текст): контракт скорера из раздела 7
   поле `why` не содержит и не меняется (решение автора после builder-check)
8. **claims** — до 6 проверяемых утверждений (для фактчекера)

**Фактчекинг карточки** — механика `editorial.fact_check_card` без изменений:
ok / uncertain / wrong по тексту статьи; wrong выбрасывается, фактчекер
переписывает `what_hapened` из подтверждённого; uncertain — корроборация через
`fetch_google_news` по query, ≥ 2 издателей → `✓ (подтверждено другими СМИ)`
и ссылки в доп. источники (≤ 3, свой url исключён). Без AI или при обрыве —
claims уходят в «требует проверки» нетронутыми.

Статус проверки в карточке выводится из фактчекинга: все claims ok →
**«подтверждено»**; есть uncertain с корроборацией → **«частично
подтверждено»**; иначе — **«требует проверки»**.

Отличие от буквы инструкции (раздел 6): там фактчекинг до включения в
подборку. Здесь скоринг уже прогоняет материал по полному тексту, а глубокая
сверка и корроборация происходит при построении карточки — то есть до того,
как редактор возьмёт тему в работу, но после списка. Это осознанный компромисс:
фактчекинг каждой из ~20 кандидатских до списка стоил бы ~40 AI-вызовов на
прогон вместо ~20+2.

## 9. Рендеринг

**Список** (`render_scout_list` — по образцу `render_topic_list`):
для каждой темы номер, `[балл/10 · рубрика А–Е · приоритет/резерв]`,
one_liner, источник, `/scout N`, ссылка. Недатированные записи (HF
trending, GitHub Trending — окно по часам на них не действует) показываются
с пометкой «трендинг, дата выхода не известна» (паттерн `_fmt_date` из
`editorial.py`) — решение редактора: пул кандидатов сохраняем, риск старой
истории виден в явном виде. Футер про окно и команды.
Мало тем не «доливаем» проходными; 0 тем → подсказка расширить окно.

**Карточка** (`render_scout_card_messages`) — все 7 полей шаблона, статусы
проверки, источники кликабельные; `html.escape` везде; разрезка по абзацам
`_split_by_paragraphs` до 4096, фолбэк на plain-text при отказе Telegram
(копия паттерна `cmd_card`). Хедер `/scout`-карточки помечает рубрику А–Е
человеческим названием («Провалы и курьёзы», а не «В»).

## 10. Режимы деградации

- **Нет `GROQ_API_KEY`** — список из keyword-топа с пометкой «режим без AI»
  (как `/digest`), карточек нет (как `/card`-стаб — заголовок, ссылка, summary,
  «факты не проверены»).
- **AI упал на статье** — фолбэк keyword-оценки (`ai=False`), порог списка ≥ 1
  для такой статьи (паттерн `editorial.select_topics` — чтобы keyword-фолбэк не
  был мёртвым кодом при общем пороге 6/10).
- **Фактчекинг выбросил все пункты** — карточка строится, но с явной пометкой;
  пост никто не отправляет автоматически — решение всегда за редактором.

## 11. Что осталось имплементатору

- Проверить/подобрать реальные URL RSS-лент из таблицы раздела 5 (особенно
  IEEE Spectrum, MIT TR, arXiv); для HF Papers — парсер или честный отказ.
- Точные составы `SCOUT_KEYWORDS` и веса (покрыть все рубрики А–Е).
- Тексты промптов скорера и карточки (в этой спеке — контракты JSON и
  критерии, формулировки — за автором).
- Кэш: повторный `/scout` без аргумента в течение сессии — пересбор бесплатен?
  НЕТ: `/scout` всегда пересобирает (AI-вызовы на скоринг), но карточка
  кэшируется в `topic["card"]`; если пересбор дорог — можно добавить
  `scout_cache` по образцу `tools_cache` (решение имплементатора, дефолт —
  как у `/digest`: пересбор всегда).
- Тесты в `tests/test_scout.py` по образцу `test_editorial.py`: валидация
  JSON-скорера (в т.ч. total пересчитан, «пустышка» отброшена), пороги
  8/6/отбой, карточный парсер с дефолтами, фактчекинг-механика, рендер
  списка/карточки c escape и лимитом.
